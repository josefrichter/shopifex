1What even is a Shopify app?

A merchant runs their store on Shopify. An app adds features to that store — here, a dashboard of best-selling products. The interesting part: your app doesn't replace the Shopify admin, it lives inside it.

When a merchant clicks your app, Shopify loads your web page in an <iframe> embedded in the Shopify admin. So your app is just a normal Phoenix app — with three twists:

  • It runs in an iframe. Browsers block third-party cookies there, so you can't lean on a cookie session the usual way.
  • Shopify proves who the merchant is with a short-lived signed token (a JWT called an id_token) that App Bridge attaches to every page load.
  • To call Shopify's API (to read products, orders, etc.) your app needs an access token for that shop. You get one through managed installation.
The good news Shopifex handles all three of these for you. You mostly write normal LiveView. The next two sections explain what's happening under the hood so it isn't magic — then we build.

2How login works (managed installation)

Older Shopify apps did an OAuth redirect dance. Modern apps — and Shopifex 3.0 by default — use managed installation with token exchange. The flow on every page load looks like this:

1
Merchant opens your appShopify renders your /auth URL in an iframe, with an id_token.
→
2
Shopifex verifies itThe :managed_install plug checks the id_token's signature.
→
3
Token exchangeFirst time? It swaps the id_token for a long-lived offline access token and saves the shop.
→
4
Your LiveView renders@current_shop is ready. You call the Shopify API and draw the page.

You don't write any of steps 1–3. You add a few lines of router wiring (the auth_routes macro does the heavy lifting, coming up) and Shopifex runs the flow. Access tokens now expire, so Shopifex also refreshes them in the background — you never think about it.

Wait — what are these tokens?

This part trips everyone up, and it isn't Shopifex-specific. There are two different tokens doing two different jobs:

  • The session token (id_token) proves who is asking. It's a tiny signed JWT that App Bridge hands your frontend on every load and attaches to requests to your backend. It's short-lived (~1 minute) and basically says "this really is shop xyz.myshopify.com, inside the Shopify admin." It is not an API key — you can't call the Shopify API with it.
  • The access token lets you actually do things. It's the real credential for the Admin API. Your backend gets one by doing token exchange: handing Shopify a valid session token and receiving an access token back (this is the OAuth 2.0 "token exchange" standard, RFC 8693).

Access tokens come in two flavors. Online tokens are tied to the logged-in user and die when they log out (good for "act as this person"). Offline tokens belong to the shop and keep working in the background — that's what embedded apps use for API calls, webhooks, and scheduled jobs. As of 2026, offline tokens also expire (≈1 hour) and ship with a 90-day refresh token to mint a new one. Shopifex stores all of that and rotates it for you.

Why this whole dance instead of a normal login cookie? Because your app renders in an <iframe> on Shopify's domain, where browsers block third-party cookies — so there's no reliable cookie session to keep. Instead, Shopify re-proves identity on every request with a fresh signed token. Shopify's session-token and token-exchange docs go deeper.

Mental model Session token = an ID badge you re-show at every door (proves who you are, expires in a minute). Access token = the keycard that actually opens doors (Shopifex keeps it charged). Token exchange is trading the badge for the keycard. And @current_shop is just "the logged-in shop" — every API call runs as it.

3Prerequisites

You'll need a few free things before writing code:

  • A Shopify Partner account — sign up at partners.shopify.com. Free.
  • A development store — create one from the Partner dashboard. It's a fake store you can install your app on and place test orders in.
  • An app in the Partner dashboard — this gives you an API key and API secret key. (The Shopify CLI can scaffold this and manage your shopify.app.toml, but it's optional.)
  • A Phoenix 1.8 app with Ecto and a Postgres database.
  • A public tunnel to your local machine — ngrok or cloudflared. Shopify must reach your dev server over HTTPS, so note your tunnel URL (e.g. https://your-app.ngrok.io).
Heads up Everything below assumes a dev store. Real ("production") apps have extra review requirements — Shopifex ships the mandatory GDPR webhook handlers so you start on the right foot, but you'll still need protected-customer-data access for orders (see §4) and Shopify's app review before going live.

4Install Shopifex

Add the dependency and run the installer.

mix.exs 
def deps do
  [
    {:shopifex, github: "josefrichter/shopifex"}
  ]
end
mix deps.get
mix shopifex.install   # generates the Shop/Plan/Grant schemas + a migration
mix ecto.migrate

The installer prints config and router snippets — here's the shape of each. First, configuration:

config/config.exs 
config :shopifex,
  app_name: "Bestsellers",
  shop_schema: MyApp.Shop,
  repo: MyApp.Repo,
  web_module: MyAppWeb,
  # Scopes Shopifex's EnsureScopes plug checks for. Keep this in sync with the
  # [access_scopes] you declare in shopify.app.toml (below).
  scopes: "read_orders,read_products",
  # Topics Shopify subscribes you to on install. We want order events.
  webhook_topics: ["app/uninstalled", "orders/create"],
  webhook_uri: "https://your-app.ngrok.io/webhook",
  api_version: "2026-04",
  api_key: System.get_env("SHOPIFY_API_KEY"),
  secret: System.get_env("SHOPIFY_API_SECRET")
These are your app's choices webhook_topics and scopes are picked for this tutorial. In your own app you'll swap in whatever events and data you need — but always keep "app/uninstalled" in webhook_topics (so you can clean up when a merchant removes your app), and only request scopes you actually use (Shopify's review gets stricter the more you ask for).

Next, declare the access scopes your app needs. With managed installation Shopify grants scopes from your shopify.app.toml at install time — and Shopifex's EnsureScopes check compares against the matching scopes: config above, so keep the two in sync. We need to read orders and products:

shopify.app.toml 
[access_scopes]
scopes = "read_orders,read_products"
Make the scope edit take effect Editing shopify.app.toml alone does nothing until you deploy it — run shopify app deploy (or set the scopes in the Partner dashboard if you aren't using the CLI). Shopify then grants them the next time the merchant opens the app.
Production note read_orders is protected customer data. It works freely on a development store, but a public app must request protected-customer-data access and pass Shopify's review before reading live orders in production.

What about the Shopify CLI?

Shopify's CLI is built around its JavaScript templates, but a couple of commands are still handy for a Phoenix app — and one you can skip:

  • shopify app config link — pulls your app's settings from the dashboard into a local shopify.app.toml. Run it once to create the file.
  • shopify app deploy — pushes shopify.app.toml (access scopes, app config) up to Shopify and cuts an app version. This is how a scope change reaches production. It does not deploy your Phoenix server — you host that yourself (Fly, Gigalixir, …). (shopify app config push was removed; deploy replaces it.)
⛔ Don't use shopify app dev with an Elixir app The CLI's all-in-one shopify app dev assumes a Node project — it expects a package.json, injects PORT/BACKEND_PORT env vars, and wants to own the dev server and tunnel itself. That doesn't fit Phoenix. Start the server and tunnel yourself instead: run mix phx.server in one terminal (your app on localhost:4000) and ngrok http 4000 in another, then put the tunnel's HTTPS URL in both the Partner-dashboard App URL and the webhook_uri config. (There's also no shopify app install command — you install onto a dev store just by opening the app and accepting the permission prompt.)

5Your first app load

First, give Phoenix the credentials your config reads. In the Partner dashboard open this app's API credentials page, copy the API key and API secret key, and export them in the same shell you'll start Phoenix from (they must belong to the app whose App URL you set below): 

export SHOPIFY_API_KEY=your_api_key
export SHOPIFY_API_SECRET=your_api_secret_key

For a permanent setup, read them in config/runtime.exs instead of exporting each time.

Then point your app's "App URL" in the Partner dashboard at https://your-app.ngrok.io/auth, start Phoenix (mix phx.server) and your tunnel, and open the app from your dev store's Apps menu. On that first open, Shopifex:

  1. verifies the id_token,
  2. exchanges it for an offline access token,
  3. saves a Shop row (URL + token + scopes),
  4. subscribes your webhook topics, and
  5. renders BestsellersLive at /.
Keep three things in sync Wherever you see your-app.ngrok.io, use your current tunnel host — identical in three places: the config webhook_uri, the Partner-dashboard App URL, and the running tunnel. ngrok's free URLs change on every restart, so re-paste the new host in all three when it does.
Blank screen or an error? The first embedded load is where setup mistakes surface. Check that (1) SHOPIFY_API_KEY / SHOPIFY_API_SECRET are set and belong to this app, (2) the App URL ends in /auth and points at your current tunnel, (3) both the tunnel and mix phx.server are running, and (4) your server log shows the id_token being verified (not a redirect loop).

6Build the Bestsellers view

"Bestsellers" = which products sold the most units recently. Shopify has no single "bestsellers" field, so we'll ask for recent orders, look at their line items, and tally quantities per product. That's a great example because it's a real GraphQL query plus a little Elixir.

The data layer

Keep Shopify calls out of your LiveView. A small context function runs the query through Shopifex.API.graphql/3 — the library's one entrypoint for the Admin API, which keeps the shop's access token fresh for you and returns {:ok, data} or {:error, reason}.

lib/my_app/analytics.ex 
defmodule MyApp.Analytics do
  @moduledoc "Bestseller analytics for a shop."

  @query """
  query Bestsellers($orders: Int!) {
    orders(first: $orders, sortKey: CREATED_AT, reverse: true) {
      edges {
        node {
          lineItems(first: 100) {
            edges { node { title quantity } }
          }
        }
      }
    }
  }
  """

  @doc "Top `limit` products by units sold across the last `sample` orders."
  def bestsellers(shop, limit \\ 5, sample \\ 100) do
    case Shopifex.API.graphql(shop, @query, %{orders: sample}) do
      {:ok, data} ->
        rows =
          data
          |> line_items()
          |> tally()
          |> Enum.sort_by(fn {_title, qty} -> qty end, :desc)
          |> Enum.take(limit)
          |> Enum.map(fn {title, qty} -> %{title: title, qty: qty} end)

        {:ok, rows}

      {:error, reason} ->
        {:error, reason}
    end
  end

  # Flatten every order's line items into one list.
  defp line_items(data) do
    for %{"node" => order} <- data["orders"]["edges"],
        %{"node" => item} <- order["lineItems"]["edges"],
        do: item
  end

  # Sum quantity per product title -> %{title => total_qty}.
  defp tally(items) do
    Enum.reduce(items, %{}, fn %{"title" => title, "quantity" => qty}, acc ->
      Map.update(acc, title, qty, &(&1 + qty))
    end)
  end
end

The LiveView

Because the route is inside shopifex_live_session, the shop is already in socket.assigns.current_shop on mount. Fetch the rows and assign them:

lib/my_app_web/live/bestsellers_live.ex 
defmodule MyAppWeb.BestsellersLive do
  use MyAppWeb, :live_view
  alias MyApp.Analytics

  @impl true
  def mount(_params, _session, socket) do
    {:ok, load(socket)}
  end

  defp load(socket) do
    case Analytics.bestsellers(socket.assigns.current_shop) do
      {:ok, rows} -> assign(socket, rows: rows, error: nil)
      {:error, _reason} -> assign(socket, rows: [], error: "Couldn't load orders.")
    end
  end

  @impl true
  def render(assigns) do
    ~H"""
    <div class="dashboard">
      <h1>🏆 Bestsellers</h1>
      <p :if={@error} class="error">{@error}</p>

      <table>
        <thead>
          <tr><th>#</th><th>Product</th><th>Units sold</th></tr>
        </thead>
        <tbody>
          <tr :for={{row, i} <- Enum.with_index(@rows, 1)}>
            <td>{i}</td>
            <td>{row.title}</td>
            <td>{row.qty}</td>
          </tr>
        </tbody>
      </table>
    </div>
    """
  end
end

Open the app and you've got a live table of bestsellers. Place a test order in your dev store, refresh, and watch it change. Next we'll make it prettier — then make it update without a refresh.

Empty table? A brand-new dev store has no orders. Create a product, then place a test order or two from the store's admin so there's something to rank.

7Add the chart (no JavaScript)

The fun thing about LiveView: the server already has the numbers, so a bar chart is just HTML and CSS — no charting library, no JS hook. Each bar's width is a percentage of the top seller. Add a helper and a chart block to the same LiveView.

lib/my_app_web/live/bestsellers_live.ex (additions) 
# A percentage width relative to the #1 seller.
defp pct(qty, rows) do
  # Only ever called while iterating non-empty @rows, so Enum.max/1 is safe.
  max = rows |> Enum.map(& &1.qty) |> Enum.max()
  round(qty / max * 100)
end

And the markup — drop this above the table in render/1:

inside ~H""" ... """ 
<div class="chart">
  <div :for={row <- @rows} class="bar-row">
    <span class="bar-label">{row.title}</span>
    <div class="bar-track">
      <div class="bar-fill" style={"width: #{pct(row.qty, @rows)}%"}></div>
    </div>
    <span class="bar-value">{row.qty}</span>
  </div>
</div>

Now the CSS. On LiveView 1.2+ you can keep it right next to the component with colocated CSS — no separate app.css to hunt through. Add a <style> block at the very top of your ~H template (it must be first), tagged with a small module:

lib/my_app_web/live/bestsellers_live.ex — top of render/1's ~H 
<style :type={MyAppWeb.ColocatedCSS}>
  .bar-row { display: grid; grid-template-columns: 150px 1fr 44px;
             gap: 14px; align-items: center; margin: 8px 0; }
  .bar-track { background: #eef6f2; border-radius: 999px; height: 16px; overflow: hidden; }
  .bar-fill  { height: 100%; border-radius: 999px;
               background: linear-gradient(90deg, #00a884, #008060);
               transition: width 700ms cubic-bezier(.2,.8,.2,1); }
  .bar-value { text-align: right; font-weight: 700; font-variant-numeric: tabular-nums; }
</style>
<div class="chart">
  <!-- the bar rows from above -->
</div>

That :type points at a one-time module that tells LiveView how to extract the CSS. The simplest version passes it through unchanged (add scoping later with CSS @scope if you want it):

lib/my_app_web/colocated_css.ex 
defmodule MyAppWeb.ColocatedCSS do
  use Phoenix.LiveView.ColocatedCSS

  @impl true
  def transform("style", _attrs, css, _meta), do: {:ok, css, []}
end

At build time LiveView extracts every colocated block into one file. A phx.new app on Phoenix 1.8.8+ already wires the bundler for this — you just import it once in assets/css/app.css: 

@import "phoenix-colocated/my_app/colocated.css";

Because LiveView swaps only the changed attributes, when the numbers update the bars animate to their new lengths for free.

Don't want colocated CSS? It's optional. A phx.new app on Phoenix 1.8 also ships Tailwind (v4) + daisyUI, so you could instead style the bars with utility classes (the data-driven width still needs an inline style), or just drop the rules in app.css the old way. For a "real" charting library, push the data to a JS hook — but for a ranked bar chart, server-rendered HTML is simpler, accessible, and animates itself.

8Make it live

Two upgrades, easiest first.

8a · Auto-refresh on a timer

Re-fetch every 30 seconds. Only do this for a connected LiveView (mount runs twice — once for the initial HTML, once over the socket):

@impl true
def mount(_params, _session, socket) do
  if connected?(socket), do: :timer.send_interval(30_000, :refresh)
  {:ok, load(socket)}
end

@impl true
def handle_info(:refresh, socket), do: {:noreply, load(socket)}

That's already "live" in the LiveView sense. But polling Shopify every 30s is wasteful, and there's a lag. Let's react to the actual event instead.

8b · Real-time with webhooks + PubSub

We subscribed to orders/create back in §4. When a customer checks out, Shopify POSTs to /webhook, Shopifex verifies the HMAC and calls your handle_topic/3. We broadcast that over Phoenix PubSub. PubSub here isn't really about "many viewers" (most stores have one admin) — it's the bridge between two processes: the webhook lands in a short-lived controller process, while your dashboard is a separate, long-lived LiveView process. PubSub is how the first tells the second. Any dashboards that happen to be open all update; that's just a bonus. (MyApp.PubSub is the server mix phx.new already started in your application.ex.)

lib/my_app_web/controllers/webhook_controller.ex 
defmodule MyAppWeb.WebhookController do
  use MyAppWeb, :controller
  use ShopifexWeb.WebhookController

  # A new order came in — tell every dashboard for this shop.
  def handle_topic(conn, shop, "orders/create") do
    Phoenix.PubSub.broadcast(MyApp.PubSub, "bestsellers:#{shop.id}", :order_created)
    send_resp(conn, 200, "ok")
  end

  # Keep Shopifex's default GDPR handlers for every other topic.
  def handle_topic(conn, shop, topic), do: super(conn, shop, topic)
end
Don't drop the GDPR defaults The moment you define your own handle_topic/3, you replace all of Shopifex's clauses — including the mandatory shop/redact / customers/redact / customers/data_request handlers Shopify requires for app review. The catch-all super(conn, shop, topic) on the last line keeps them.

Now the LiveView subscribes on connect and reloads when an order lands:

@impl true
def mount(_params, _session, socket) do
  shop = socket.assigns.current_shop

  if connected?(socket) do
    Phoenix.PubSub.subscribe(MyApp.PubSub, "bestsellers:#{shop.id}")
  end

  {:ok, load(socket)}
end

@impl true
def handle_info(:order_created, socket), do: {:noreply, load(socket)}

Now place an order through the storefront's test checkout (Shopify's Bogus Gateway / a test card) — that reliably fires an orders/create webhook. With no refresh, the table re-ranks and the bars glide to their new lengths. That round trip (Shopify → webhook → PubSub → every LiveView → animated diff) is the whole promise of LiveView, and you wrote maybe 15 lines for it.

No update? Orders created from the admin (especially draft orders) often don't emit orders/create, so the live update won't fire even though your code is correct — use the storefront test checkout. Confirm the webhook arrived by watching your server log for the POST /webhook.
Tip Broadcasting a bare :order_created and re-querying is the simplest correct version. Once it works, an optimization is to send the order's line items in the message and update the tallies in memory — no extra Shopify call per order.
Is the webhook worth it? Honestly — for a single-admin store, the 30-second timer in §8a is often plenty. The webhook path earns its keep when "an order happened" should also do other things (send a notification, recompute a cache, enqueue an Oban job), or when you want zero-lag updates without hammering Shopify. Reach for it when you have a reason, not by default.

9Charge for it with PaymentGuard

Most apps want money. Shopifex's PaymentGuard is a plug you put in front of a route: if the shop hasn't paid, it redirects them to a plan-selection page, runs Shopify's checkout, records the payment, and lets them back in — you don't write any of that flow. The installer already generated the Plan and Grant schemas; here's the wiring.

config/config.exs (add) 
config :shopifex,
  payment_guard: MyApp.Shops.PaymentGuard,
  plan_schema: MyApp.Shops.Plan,
  grant_schema: MyApp.Shops.Grant,
  payment_redirect_uri: "https://your-app.ngrok.io/payment/complete"
lib/my_app/shops/payment_guard.ex 
defmodule MyApp.Shops.PaymentGuard do
  use Shopifex.PaymentGuard
  # Sensible defaults: finds grants in the DB, decrements usage, creates grants on payment.
end
lib/my_app_web/controllers/payment_controller.ex 
defmodule MyAppWeb.PaymentController do
  use MyAppWeb, :controller
  use ShopifexWeb.PaymentController
  # Renders the plan picker and handles the Shopify charge callback.
end

Add the payment routes (the plan page renders with Polaris from Shopify's CDN — nothing to serve yourself):

lib/my_app_web/router.ex (add) 
ShopifexWeb.Routes.payment_routes(MyAppWeb.PaymentController)

A plan is just a database row that grants a named capability. Create one (in iex -S mix or a seed script) — here a $9.99/month plan that grants "pro": 

Shopifex.Shops.create_plan(%{
  name: "Pro",
  price: "9.99",
  type: "recurring_application_charge",
  test: true,            # test charge — Shopify shows the approval screen but never bills
  grants: ["pro"]
})

Now protect the dashboard: add a pipeline with the guard and run the live route through it.

lib/my_app_web/router.ex 
pipeline :require_pro do
  plug Shopifex.Plug.PaymentGuard, "pro"
end

scope "/", MyAppWeb do
  pipe_through [:shopifex_browser, :shopify_session, :require_pro]

  ShopifexWeb.Routes.shopifex_live_session :embedded do
    live "/", BestsellersLive
  end
end

A shop with no "pro" grant now gets bounced to the plan picker; after they approve the charge in Shopify, a Grant row is created and they land back on the dashboard. Guards can also be usage-limited (e.g. "100 runs") via the plan's usages field.

Test charges With test: true, Shopify shows the real approval screen but never charges the card — ideal on a dev store. Flip it off for production plans.
Multi-node deploys The billing flow stores a charge_id → redirect_after entry when the charge starts and reads it back on Shopify's confirmation. The default Shopifex.RedirectAfterAgent keeps that in a node-local agent, so on a multi-node host (Fly.io, etc.) the confirmation can land on a different node, miss the cache, and the grant is never created (the merchant is still charged). Use the shipped DB-backed store instead: config :shopifex, :redirect_after_agent, Shopifex.RedirectAfter.Ecto (add its shopifex_charge_redirects table — mix shopifex.install generates the config and migration for new apps). Single-node is fine as-is; either way a missed lookup now logs a loud Logger.error instead of failing silently.

10Make it look native with App Bridge & Polaris

Right now your dashboard looks like your HTML. To make it feel like part of the Shopify admin — matching type, buttons, a real title bar, toasts — you load two small scripts Shopify hosts: App Bridge (the admin chrome plus a global shopify JS object) and Polaris web components (Shopify's design-system elements).

No React required Polaris used to mean React. As of late 2025, Polaris React is deprecated and Polaris web components are the default — plain custom HTML elements (<s-button>, <s-section>…) that work in any framework, including server-rendered LiveView. A great fit here.

Add both CDN scripts and your API-key meta tag to the embedded layout's <head>:

lib/my_app_web/components/layouts/root.html.heex (in <head>) 
<meta name="shopify-api-key" content={Application.fetch_env!(:shopifex, :api_key)} />
<script src="https://cdn.shopify.com/shopifycloud/app-bridge.js"></script>
<script src="https://cdn.shopify.com/shopifycloud/polaris.js"></script>

App Bridge auto-initializes from that meta tag — no setup code. Now wrap your dashboard in Polaris elements; s-page even renders a title bar in the admin outside your iframe:

inside BestsellersLive's render/1 
<s-page heading="Bestsellers">
  <s-button slot="primary-action">Export</s-button>

  <s-section heading="Top products">
    <!-- your existing chart + table markup goes right here -->
  </s-section>
</s-page>

The shopify global also gives you imperative bits like toasts and the product picker. From a LiveView you reach those through a tiny JS hook — e.g. show a toast when the server pushes an event: 

// assets/js/app.js — trigger from the server with push_event(socket, "toast", %{message: "Saved"})
Hooks.Toast = {
  mounted() {
    this.handleEvent("toast", ({message}) => shopify.toast.show(message))
  }
}
Use the new element names Older tutorials show <ui-title-bar> / <ui-nav-menu>. Those were renamed to the s-* components (s-page, s-app-nav, s-modal…). The App Home reference has the current set.

11Where to next

You've got a real embedded app: authenticated, calling the Shopify API, billable, native-looking, and updating in real time. From here:

  • Deploy it. Host your Phoenix app (Fly.io, Gigalixir, your own box), point the Partner-dashboard App URL at the deployed HTTPS URL, and run shopify app deploy to publish your scopes and config.
  • Understand the internals. The parity matrix shows exactly how Shopifex compares to Shopify's official JS and Ruby libraries (token exchange, HMAC, billing, and the honest gaps).
  • Read the reference. The README covers config, the payment guard, SPA mode, and LiveView setup in depth.

Official Shopify resources

Shopify maintains official libraries for Ruby, Node, PHP, Go and .NET — but not Elixir, which is exactly the gap Shopifex fills. Their tutorials and templates are all JavaScript, yet they're still the best reference for how the platform behaves:

  • Build a Shopify app (React Router) — Shopify's official getting-started tutorial.
  • shopify-app-template-react-router — the current official starter (JS/React; the older Node and Remix templates are superseded).
  • Session tokens & token exchange — the §2 auth concepts, straight from the source.
  • shopify-app-js & shopify_app (Ruby) — the official frameworks Shopifex is modeled after.
Recap The whole app was: a couple of router macros, a few small controllers, one context module, and one LiveView. Shopifex handled login, token refresh, webhook verification, billing, and GDPR compliance — so you could focus on the part that's actually yours.
